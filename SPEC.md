# Snail.MCP.Plans — ТЗ v2

## Задача

Агент перед началом работы составляет план и идёт по нему, отмечая шаги и правя план по ходу.
Из другой сессии владелец спрашивает список активных планов и насколько они продвинулись.

Сервер — для собственных сессий владельца на его машине. Он **хранит** план, а не планирует:
порядок шагов придумывает модель, сервер держит их, следит за очерёдностью и напоминает, где агент остановился.

Вычеркнуто из v1 как не следующее из задачи: экспорт завершённых планов в векторную память,
append-only журнал правок, обратный канал координатора (директивы, передача работы).

## Хранилище

Один файл SQLite + EF Core 10, `journal_mode=WAL` и `busy_timeout` — обязательны: агент это
stdio-процесс на сессию, а вторая сессия читает тот же файл одновременно.
Путь: `SNAIL_MCP_PLANS_DBPATH`, по умолчанию `~/.snail-mcp-plans/plans.db`;
`SNAIL_MCP_PLANS_BUSYTIMEOUTSECONDS` — сколько ждать чужую запись, по умолчанию 10 секунд.

### Plans

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | Guid | |
| `AgentId` | string | кто ведёт план, см. «Личность» |
| `ProjectName` | string | рабочая папка сессии, для группировки в списке |
| `Objective` | string | **неизменяемо** — цель, поставленная при создании |
| `Summary` | string? | мутабельное «где мы сейчас» |
| `Status` | enum | `Active`, `Completed`, `Failed`, `Abandoned` |
| `Version` | int | растёт на каждой записи, возвращается в ответах |
| `CreatedAt` / `UpdatedAt` / `CompletedAt` | DateTimeOffset | |

`Objective` отдельно от `Summary` потому, что в v1 единственное поле перезаписывалось и цель
терялась — агент дрейфовал от того, о чём его просили.

### Steps

| Поле | Тип | Смысл |
|---|---|---|
| `Id` | Guid | |
| `PlanId` | Guid | |
| `OrderIndex` | int | разреженный, шаг 100; ревизия перенумеровывает весь список (план пишется целиком, так что пересчёт бесплатен, а шаги цитируются по `Id`, не по позиции) |
| `Title` | string | |
| `Status` | enum | `Pending`, `InProgress`, `Done`, `Failed`, `Skipped` |
| `Note` | string? | последняя заметка: что получилось или почему нет |
| `Attempts` | int | сколько раз шаг входил в `InProgress` |
| `StartedAt` / `CompletedAt` | DateTimeOffset? | |

Переходы: `Pending → InProgress → Done | Failed | Skipped`; из `Failed` можно снова в `InProgress`
(тогда `Attempts++`); снять шаг в `Skipped` можно из `Pending`, `InProgress` и `Failed`; взятый по
ошибке шаг возвращается `InProgress → Pending` — попытка при этом сохраняется, потому что шаг
действительно брали, а без этого выхода единственным способом освободить единственный слот плана было
объявить провал, которого не было. `Done` и `Skipped` — терминальны. Остальное отклоняется с текстом,
называющим разрешённые переходы. Частичный уникальный индекс `(PlanId) WHERE Status='InProgress'` держит
инвариант «не больше одного шага в работе» в базе, а не в коде.

Шаги никогда не удаляются физически — только `Skipped` с причиной в `Note`. Иначе прогресс,
который спрашивает вторая сессия, можно улучшить удалением неудобных шагов.

## Личность

`AgentId` берётся из env процесса `SNAIL_MCP_PLANS_AGENTID`; если её нет — из рабочей папки
процесса (клиент запускает stdio-сервер в папке проекта). Параметром тула — никогда: значение
придумывает модель, и тогда любой агент читает чужой план, назвав чужой id.
Дефолт по папке выбран так, чтобы env не приходилось прописывать в каждом проекте.

Режима `--coordinator` нет: владелец один на своей машине, ограничивать нечего, а второй режим
процесса — лишняя настройка клиента. `list_active_plans` доступен всем.

## Тулы (пять)

**`create_plan(objective, steps[])`** → `plan_id`, версия, первый шаг.
Один `Active` план на пару (агент, проект): при попытке создать второй возвращается существующий
с пометкой, называющей вызов закрытия (`revise_plan` с `outcome`) — так повторный вызов по таймауту MCP
(доставка at-least-once) не плодит дублей. Если в проекте активен план ДРУГОГО агента, план создаётся
(это законно), но ответ называет чужой план с его `plan_id` и целью — чтобы на него смотрели, а не
заводили свой по ошибке.

**`get_current_plan(project_name?, plan_id?)`** — **без аргументов** отвечает по личности из env: цель,
`Summary`, все шаги со статусами, текущий шаг, версия. Это вход после сброса контекста: `plan_id` жил в
схлопнувшемся диалоге, и без такого тула агент просто заведёт второй план.
С `plan_id` читает ЛЮБОЙ план, включая чужой, и помечает его «только чтение» с именем агента: список
активных отдаёт лишь сводку, а без этого сессия из другой папки звала `create_plan` «чтобы посмотреть»
и оставляла мусорный дубликат.

**`update_step(step_id, status, note?)`** → прогресс + **следующий `Pending` шаг**.
Без `plan_id` и без `version`: план находится по личности, а конфликт записи разрешается внутри вызова.
Возврат следующего шага в том же ответе — главная экономия здесь: «отметил и узнал, что дальше» это
один вызов, а не два. При `Failed` в ответ добавляется подсказка: повторить, пропустить с причиной
или вставить шаг перед этим.

**`revise_plan(plan_id, version, changes[], summary?, outcome?)`** → новый состав плана.
Изменения: `Add` (в конец или после указанного шага), `Edit` (переформулировать `Title`),
`Skip` (снять с причиной), `Reorder`. Терминальные шаги правке и снятию не подлежат.
`version` обязателен: если план изменился с момента чтения, запись отклоняется — иначе две
параллельные правки молча теряют одну. Правит только тот агент, который ведёт план.
Ответ печатает `added N:` со `step_id` каждого созданного шага ДО самого плана: на длинном плане список
шагов не влезает в ответ, и именно id только что добавленных оказывались за обрезкой.
Несколько `Add` с одним `after` ложатся в порядке перечисления (каждый за предыдущим), а `Reorder` с
`after` ставит шаг ровно за указанным — цепочка применяется только к добавлениям.
`summary` обновляет «где мы сейчас»; `outcome` объявляет исход плана — см. «Закрытие плана».

**`list_active_plans(project_name?)`** — то, что зовёт вторая сессия. По каждому активному плану:
агент, проект, цель, счётчики шагов по статусам, текущий шаг, попытки, сколько назад был
`UpdatedAt`. Процент `Done/всего` — не показывать: им врут правкой состава; честный ответ это
счётчики плюс возраст активности, по которому видно зависшего агента.

У каждого тула — предел размера ответа (20 000 символов) с **явным маркером усечения** в тексте.
Заметки терминальных шагов печатаются усечёнными до 120 символов, у открытых — целиком: замерено на
планах в 46 и 79 шагов, где заметки сделанного съедали ответ и id поздних шагов приходилось доставать
из базы руками.

## Закрытие плана

В ТЗ v1 ни один тул не переводил план в терминальный статус — дыра, закрытая здесь **без шестого тула**.

Статус плана выводится из шагов: как только не осталось ни одного открытого шага (`Pending`,
`InProgress`) и ни одного `Failed`, план сам становится `Completed`. Добавление шага в завершённый план
снова делает его `Active` — иначе авто-закрытие было бы ловушкой для агента, вспомнившего ещё один шаг.

`Failed` намеренно не считается терминальным: план с провалившимся шагом остаётся `Active`, пока агент
не повторит шаг или не снимет его с причиной. Так провал нельзя оставить позади молча.

Досрочный исход объявляет агент — `revise_plan(outcome: Failed | Abandoned | Completed)`; `Active`
переоткрывает план. Объявленный исход сильнее шагов: агент сказал, что работа не вышла, и дорабатывать
остаток не требуется.

## Доставка протокола агенту

Без инструкции сервер не зовут: на Snail.MCP.Roslyn замерена адоптация 6%.
`McpServerOptions.ServerInstructions` (≈350 токенов один раз за сеанс) говорит: перед работой над
многошаговой задачей — `create_plan`; в начале сеанса и после сброса контекста — `get_current_plan`;
после каждого шага — `update_step`, и следующий шаг брать из его ответа; отклонение от плана
оформлять `revise_plan`, а не молча.

## Приёмка

Выполнена: **125 тестов**, 0 предупреждений сборки.

- `StdioContractTests` по реальному процессу: чистый stdout, все пять тулов в `tools/list` под
  wire-именами, инструкция доезжает в `initialize`, конфигурация дошла до хранилища, и целый план
  проходится через провод (черновик → возврат без `plan_id` → отметка шага → список активных).
- Reflection-guard тесты: добавление значения в `StepStatus`, `PlanStatus` или `ChangeKind` роняет тест,
  пока описание тула его не назовёт; лимит вывода в прозе сверяется с константой; каждый тул и каждый
  его параметр обязаны иметь описание; ровно пять тулов.
- Таблица переходов, включая отказы и невозможность прыжка `Pending → Done`.
- Частичные уникальные индексы — проверены на реальном файле: второй `InProgress` в одном плане и
  второй активный план одного агента в одном проекте не записываются.
- Конфликт версий у `revise_plan` и в самом хранилище.
- `create_plan` дважды подряд → один план.
- Файл открыт в режиме WAL — проверено чтением `PRAGMA journal_mode` на реальной базе.
- Возраст последней записи в списке активных планов; отсутствие процента в ответе.
- Доработки по следам эксплуатации: два `Reorder` в одном вызове применяются оба; пачка `Add` с одним
  `after` держит порядок; возврат шага в `Pending` не выдумывает провал и сохраняет попытку; план из 60
  шагов с 55 закрытыми печатается без обрезки; чужой план читается по `plan_id` и помечается; `create_plan`
  называет чужие активные планы. Каждый из этих тестов проверен КРАСНЫМ до правки.
